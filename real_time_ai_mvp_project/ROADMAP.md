# ROADMAP

このドキュメントは「今、何を作るべきか」を迷わないための開発計画書である。

Claude Code等のAIエージェントに実装を依頼する際は、
**必ず現在のSprintの範囲内だけを依頼すること。** 先のSprintに手を出させない。

---

## Sprint一覧

| Sprint | 内容 | Phase | 状態 |
| --- | --- | --- | --- |
| 1 | PWA + マイク入力 | Phase1 | 実装済み(実機確認待ち) |
| 2 | 音声ストリーミング | Phase1 | 実装済み |
| 3 | リアルタイム文字起こし | Phase2 | 実装済み(実API検証待ち) |
| 4 | Markdown生成 | Phase3 | 実装済み |
| 5 | オーケストレーター | Phase4 | 実装済み |
| 6 | MVP生成 + 配信・URL表示 | Phase5 + Phase6 | 実装済み |
| 7 | 営業デモ完成 | (Phase外・仕上げ) | 実装済み(実API検証待ち) |

Sprint 1〜6 が README.md にある「最初の完成形」に対応する。
Sprint 7 で実際の商談に持ち込める状態にする。

---

## 進め方の原則

- **1 Sprint = 動くものが1つ増える。** 動かないものを次のSprintへ持ち越さない。
- **完了条件を満たすまで次へ進まない。** 各Sprintの「完了条件」がチェックリストの正本。
- **外部APIはすべてモックから始める。** 本物に繋ぐのは、その部分が主題のSprintになってから。
- 設計変更が必要になったら、実装より先に該当ドキュメントを更新する。

# Sprint 1: PWA + マイク入力

**目的**: ブラウザで音声が取れることを確認する。サーバーはまだ関与しない。

## 作るもの

- PWAの雛形(インストール可能、オフラインで起動する)
- マイク権限の要求と、許可・拒否のハンドリング
- MediaRecorder による録音開始 / 一時停止 / 再開 / 停止
- 録音中であることの常時表示(プライバシー要件)
- 録音した音声のローカル再生(取れていることの目視確認用)

## 完了条件

- [x] マイク権限を許可すると録音が始まる
- [x] 拒否した場合にエラーメッセージが出て、アプリが壊れない
- [x] 一時停止・再開が動作する
- [x] 録音中インジケータが常に見えている
- [x] 録音した音声をその場で再生できる
- [ ] **スマートフォンのブラウザからインストールできる** ← 実機確認が残っている

manifest がインストール要件(name / start_url / display:standalone / icons)を満たすこと、
Service Worker が登録されオフラインで起動することは Chromium で検証済み。
実機での確認には HTTPS 配信が必要(手順は `app/README.md`)。

### 検証方法

```bash
cd app
npm test           # 状態遷移の単体テスト
npm run build
npm run preview    # http://127.0.0.1:4173
```

実ブラウザでの通し確認(録音 → 一時停止 → 再開 → 停止 → 再生、
権限拒否時の挙動、オフライン起動)は Chromium の fake media device で実施済み。

## やらないこと

サーバー通信、文字起こし、Markdown。

# Sprint 2: 音声ストリーミング

**目的**: 音声が途切れずサーバーへ届き、切断しても復帰することを確認する。

## 作るもの

- Gateway Server の雛形(Node.js / TypeScript)
- `POST /api/v1/sessions` によるセッション作成とトークン発行
- WebSocketエンドポイントと制御メッセージ(`start` / `pause` / `resume` / `stop` / `ping`)
- 音声チャンクの送信(Opus / 250msごと)
- 指数バックオフによる自動再接続、切断中の最大60秒バッファ
- サーバー側でチャンクを受信できていることのログ出力

## 完了条件

- [x] PWAからWebSocketへ接続し、音声チャンクが連続して届く
- [x] 機内モードのON/OFFで切断させても、自動的に再接続する
- [x] 切断中の音声が再接続後に送信される(60秒以内の場合)
- [x] `pause` 中は音声が送られない
- [x] 不正なトークンで `4401` が返る
- [x] **30分連続で接続を維持できる**

Sprint 7 の通しリハーサルで達成。30分の連続稼働で 6072 チャンク / 約29MB を受信し、
切断・停滞・JSエラーいずれもゼロ。ping 周期(30秒)を60回またいでいる。

### 検証方法

```bash
npm install          # ルートで1回
npm test             # 全ワークスペースの単体・結合テスト

# 実機相当の通し確認
npm run dev --workspace server   # :8787
npm run dev --workspace app      # :5173 (/api と /ws を :8787 へproxy)
```

実ブラウザでの通し確認(接続、チャンク連続受信、pause中の停止、
切断→バッファ→再接続での再送、4401)は Chromium で実施済み。
切断の再現には Playwright の `routeWebSocket` を使う
(Chromium の `setOffline` は確立済みWebSocketを切らないため)。

## やらないこと

文字起こし。この時点ではサーバーは受信するだけでよい。

# Sprint 3: リアルタイム文字起こし

**目的**: 商談で使える遅延と精度で文字起こしが画面に出ることを確認する。

## 作るもの

- `SpeechProvider` インターフェースと、モック実装 + 実API実装
- STT Proxy(音声チャンクの中継、partial / final の受領)
- `transcript.partial` / `transcript.final` のPWAへの配信
- PWA側のリアルタイム表示(確定テキストの追記、未確定テキストの薄字表示)
- 話者ラベルの表示(取得できる場合)

## 完了条件

- [x] 発話終了から3秒以内に確定テキストが画面へ出る
- [x] 未確定テキストが確定テキストへ置き換わる際に表示が乱れない
- [x] STT APIを停止させた場合、エラーが表示され、アプリが落ちない
- [x] モック実装に差し替えてもPWA側のコードを変更せずに動く
- [ ] **30分の会話を通して文字起こしが破綻しない** ← 長時間確認が残っている
- [ ] **話者分離の精度を実測し、採否を判断する** ← 実APIの資格情報が必要

### 実APIの検証が残っている

開発環境に音声認識の資格情報が無いため、既定は `MockSpeechProvider`(台本ベース)。
`DeepgramSpeechProvider` は型・接続手順・イベント整形まで用意したが、
**実接続は未確認**。資格情報が用意でき次第、次を実施する。

1. `SPEECH_PROVIDER=deepgram DEEPGRAM_API_KEY=... npm run dev --workspace server`
2. 2〜3人の模擬商談で話者分離の精度を実測し、採否を RETROSPECTIVE.md に記録する
3. 30分の会話で破綻しないことを確認する

### 検証方法

```bash
npm test                          # 単体・結合テスト

npm run dev --workspace server    # 既定は SPEECH_PROVIDER=mock
npm run dev --workspace app

# 音声認識が落ちたときの縮退動作を再現する
SPEECH_FAIL=true npm run dev --workspace server
```

実ブラウザでの通し確認(partial→finalの置き換え、話者ラベル、再接続時の
取りこぼし無し、STT停止時の縮退)は Chromium で実施済み。

## やらないこと

Markdownへの保存。この時点では表示のみでよい。

# Sprint 4: Markdown生成

**目的**: すべてのデータがMarkdownに落ちる状態を作る。ここがプロジェクトの背骨になる。

## 作るもの

- Markdown Store(セッション単位のディレクトリ、読み書きAPI)
- `meeting.md` / `transcript.md` の生成と追記
- DATAFLOW.md のスキーマに沿ったフォーマット
- `GET/PUT /api/v1/sessions/{id}/documents/{name}`
- 差分処理のカーソル管理(処理済みバイト位置)
- 全文置換時のアトミックな書き込み

## 完了条件

- [x] 確定テキストが5秒以内に `transcript.md` へ反映される
- [x] `transcript.md` が追記専用で、既存行が書き換わらない
- [x] 再接続後に重複した行が入らない
- [x] 手入力(`PUT`)でMarkdownを修正できる
- [x] セッション終了後もMarkdownが読み出せる
- [x] ファイル所有者(AGENTS.md)のルールに違反する書き込みができない

## やらないこと

LLM呼び出し。まだAIは1つも動かさない。

## 実装メモ

`server/src/markdown/` に置いた。

| ファイル | 役割 |
| --- | --- |
| `documents.ts` | 登録簿。AGENTS.md の所有者表と追記/置換の区別を実行可能にしたもの |
| `format.ts` | DATAFLOW.md のスキーマの整形(純粋関数) |
| `store.ts` | ファイル入出力、アトミックな置換、差分カーソル |
| `sessionDocuments.ts` | セッションの出来事をMarkdownへ落とす層。入力アダプタもここ |

決めたこと:

- **`transcript.md` への `PUT` は `409`。** 追記専用と全文置換は経路を分ける。
  会話への補足は `POST /inputs` から入れる(DATAFLOW.md の入力アダプタを更新した)。
- **セッション記録とMarkdownの寿命を揃えた。** どちらも既定30日。
  片方だけ消えると「トークンはあるのに中身が無い」状態になる。
- **確定テキストの保存に失敗しても文字起こしは止めない。** 画面には出続け、欠けたことはログに残る。

積み残し:

- ~~サーバーを再起動するとセッションのトークンが失われ、Markdownが残っていても読めない。~~
  → 解消(Sprint 7 の運用準備)。メタ情報を `session-meta/` へ永続化した。
- `- participants:` は空のまま。入力経路が無い(Sprint 5 以降)。

# Sprint 5: オーケストレーター

**目的**: 商談中に課題と要件がリアルタイムで積み上がる状態を作る。ここが最初のデモ価値になる。

## 作るもの

- `LLMProvider` インターフェースと実装
- AI Orchestrator(起動条件の判断、差分の切り出し、結果のマージ)
- Issue Agent(60秒ごとに `issues.md` / `ideas.md` を更新)
- Requirement Agent(`requirements.md` の生成)
- UI Agent(`ui.md` の生成)
- Transcript Agent(`summary.md` / `todo.md` の生成。セッション終了時)
- `document.updated` のPWAへの配信とリアルタイム表示
- Agent実行履歴のログ保存

## 完了条件

- [x] 60秒ごとに `issues.md` が更新され、PWAへ反映される
- [x] 同じ課題が二重に追加されない
- [x] 差分のみがLLMへ投入されている(ログで確認できる)
- [x] `requirements.md` が1〜3画面のスコープに収まっている
- [x] LLM APIを停止させても文字起こしは継続する
- [x] 各Agentが自分の所有ファイル以外へ書き込んでいない
- [x] Agent実行履歴(入力・出力・所要時間・モデル)が保存されている

## やらないこと

コード生成、デプロイ。

## 実装メモ

`server/src/llm/` と `server/src/agents/` に置いた。

| ファイル | 役割 |
| --- | --- |
| `llm/types.ts` | `LLMProvider` の抽象。使用量(トークン)も返す |
| `llm/mockLLMProvider.ts` | 規則ベースのモック(既定)。**資格情報なしで経路全体を通せる** |
| `llm/anthropicLLMProvider.ts` | Claude API 実装(⚠️ 実接続は未検証) |
| `agents/prompts.ts` | 各Agentの指示。AGENTS.md の責務表をそのまま指示にしたもの |
| `agents/orchestrator.ts` | 起動条件・差分の切り出し・マージ・履歴 |
| `agents/history.ts` | Agent実行履歴(JSON Lines) |
| `markdown/items.ts` | `issues.md` / `ideas.md` のマージ規則 |

決めたこと:

- **`LLMProvider` は使用量(トークン数)も返す。** RETROSPECTIVE.md の未解決の論点
  「商談終了時の差分再生成」はコストを測ってから決めると置いている。測れない設計にしない。
- **課題の突き合わせは見出しで行い、IDはこちらで採番する。**
  LLMに採番させると、実行のたびに同じ課題の番号が入れ替わる。
- **`document.updated` は通知だけで、本文は載せない。**
  PWAが `GET /documents/{name}` で取り直す。切断中の更新を取りこぼさない。
- **Requirement Agent の起動口として `POST /generate` を先に作った。**
  Sprint 6 の予定だったが、Requirement / UI Agent を動かす手段が無いと完了条件を確かめられない。
  Sprint 6 でトリガー検出・明示承認UI・コード生成の段階を後ろに繋ぐ。
  `confirm: true` を必須にしてあるため、承認なしで動く口にはなっていない。

積み残し:

- **実LLM APIでの検証。** 資格情報が無いため `AnthropicLLMProvider` は実接続を確認していない。
  ただし公式仕様との突き合わせは済ませ、初回接続で必ず出る3点を直した(2026-08-02):
  拒否応答(HTTP 200 で `content` が空)を再試行しない失敗として扱う / 上限切れの
  途中出力を受け取らない / `max_tokens` を 4096 → 16000(思考と本文の合計にかかるため)。
  キーが入ったら `node scripts/verify-llm.mjs` で出力形式・所要時間・トークン量を一度に測れる。
- **プロンプトキャッシュは現状のプロンプト長では効かない。** 最小サイズ(Sonnet 5 は1024、
  Opus 5 は512トークン)に対し、各Agentの指示は190〜530文字しかない。`context.md` が
  大きい商談でのみ効く。印は付けたまま(大きくなれば自動的に効く)。
- 抽出の質は実APIでしか測れない。モックは形の検証にしか使えない。

# Sprint 6: MVP生成 + 配信・URL表示

**目的**: 要件定義から動くWebアプリが生まれ、自分のタブレットで開ける状態にする。

Phase5(MVP生成)と Phase6(デプロイ・URL表示)の両方を含む。
URLが出ないMVP生成には価値がないため、分割せず1Sprintで通す。

## 作るもの

- トリガーキーワード検出と `trigger.detected` の配信
- **明示承認の確認UI**(自動承認はしない。タップされるまで生成しない)
- `POST /api/v1/sessions/{id}/generate` と生成ジョブ管理
- Claude Code Agent(`requirements.md` + `ui.md` → ソースコード。静的SPA限定)
- Review Agent(`review.md` の生成、`[BLOCK]` による差し戻し)
- Claude Code ⇄ Review の再試行ループ(最大3回)
- `DeployProvider` と Deploy Agent(既定実装 = Gateway Serverによる静的配信)
- `GET /preview/{sessionId}/{buildId}/*` とトークン検証
- `artifact.ready` の配信、URLとQRコードの表示
- 失敗時のZIPダウンロード提供

## 完了条件

- [x] 承認から30秒以内に生成が開始される
- [x] **承認するまで生成が始まらない**(雑談で「アプリ作って」と言っても動かない)
- [x] 誤検知時に確認UIでキャンセルできる
- [x] 生成が商談中に並行して走り、商談終了を待たない
- [x] 承認から10分以内にURLが提示される
- [x] 生成されたアプリが静的ビルドで通る(SSRを使っていない)
- [x] `[BLOCK]` があった場合に差し戻され、修正される
- [x] トークンなしで `/preview/...` へアクセスすると `401` が返る
- [x] QRコードから自分の別端末でアプリを開ける(実機での読み取りは未確認)
- [x] セッション失効後にURLへアクセスすると配信が停止している
- [x] 3回失敗した場合に、要件定義までを成果物として提示する
- [x] 生成コードにシークレットが含まれていない

## やらないこと

Circleback / Notion 連携。

## 実装メモ

| 場所 | 役割 |
| --- | --- |
| `server/src/agents/trigger.ts` | トリガーキーワードの検出 |
| `server/src/codegen/` | `CodeProvider` の抽象、雛形生成(既定)、LLM生成、**検証** |
| `server/src/deploy/` | `DeployProvider` と Gateway 自身による静的配信 |
| `server/src/http/preview.ts` | `/preview/...` の配信とトークン検証 |
| `server/src/http/zip.ts` | 持ち帰り用のZIP(依存なし・無圧縮) |
| `app/src/qr/encode.ts` | QRコードの生成(自前) |
| `app/src/components/TriggerConfirm.tsx` | 明示承認の確認UI |
| `app/src/components/Artifact.tsx` | 進捗・URL・QR |

決めたこと:

- **生成物にビルド工程を持たせない。** 素の HTML / CSS / JavaScript に限定した。
  商談中に `npm install` を走らせると、回線とサーバー(メモリ2GB)次第で10分の予算を使い切る。
  `ai_instruction.md` の既定もこれに合わせた。
- **既定のコード生成は雛形(`TemplateCodeProvider`)。** 推論しないぶん速く、必ず動くものが出る。
  実APIが落ちていても最低限の成果物が出る、縮退動作の最終防壁でもある。
- **事故を止めるのは規則(`validate.ts`)で、LLMのレビューではない。**
  外部参照・サーバーサイド実行・シークレットは必ず規則で弾く。
  Review Agent の指摘はその上に積む。
- **QRコードは自前で作る。** 外部のQR生成サービスへURLを送れば、
  商談内容から作られたURLを外へ出すことになる。
- **持ち帰りのZIPはトークンをURLへ載せない。** 取得してから保存させる。
- **生成の直前に Issue Agent を1回回す。** トリガーは会話の途中で飛ぶため、
  ここで追いつかせないと「今話していたこと」が要件定義に入らない。

積み残し:

- **実機でのQR読み取りは未確認。** 生成したモジュールを読み返す試験で符号化の正しさは
  確かめたが、実際のカメラで読めるかは端末が要る。
- **`LLMCodeProvider` は実接続を確認していない。** 資格情報が無いため。
- ~~生成物の形は雛形1種類。要件によらず同じ形になる。~~
  → 解消(Sprint 7)。要件から4種類(一覧 / 申請承認 / 点検 / 集計)を選び分ける。

## 実装メモ(運用準備、2026-08-02)

本番サーバーが Xserver VPS に決まったため、リハーサルに先立って運用系を固めた。

- **DEPLOY.md**: nginx(TLS終端・WebSocketアップグレード)+ systemd + 環境変数の
  構築手順。PWA・API・生成MVP配信を1サブドメイン(推奨ラベル `mvp.`)へ同一
  オリジンで載せる。マイクとPWAはHTTPS必須のため、実機確認はVPS構築後に行う
- **OPERATIONS.md**: 営業担当向けの操作手順書。同意の取り方、トリガーの言い回し、
  QRの見せ方、縮退時の振る舞い、禁止事項(実データ投入)まで
- **セッションメタ情報の永続化**: `{DATA_DIR}/session-meta/` にトークン込みで保存し、
  再起動しても記録へ到達できる。実行中だったセッションは `server_restart` で終了扱い
- **transcript追記の再送**: ディスクの一時不調で発言を失わない(2回追試 + seq関門の巻き戻し)
- **セッション作成のレート制限**: 30回/時間(既定)。トークン無しで叩ける唯一の入口を塞いだ

## 実装メモ(30分通しリハーサル、2026-08-02)

モック構成(STT・LLM・テンプレート生成)で30分を実時間で通した。
承認からURL到達まで**4秒**、30分後も生成物は200を返し、JSエラーゼロ、切断ゼロ。
文字起こし424行 / 音声27MBを送信し続けた。

**通しで初めて分かった不具合を2件直した。** どちらも短時間の検証では見えない。

- **課題の根拠が無制限に積み上がる。** 同じ話題へ会話が戻るたびに根拠が増え、
  30分で1課題あたり33件になった。重複判定はあったが、根拠の値に時刻が入るため
  同じ発言でも別物と判定されていた。時刻を外して比べ、上限3件で打ち止めにした。
  課題タブは顧客へ画面共有する場所で、根拠の羅列で埋まると課題自体が読めない
- **トリガーが59回再検出された。** そのたびに議事録の作り直し(LLM呼び出し)まで
  走っていた。確認を出した直後の3分間は次の検出を無視するようにした
  (`TRIGGER_COOLDOWN_MS`)

縮退の実地確認では、**確認ダイアログが「議事録を準備しています…」のまま止まる**
問題も見つけた。AIが停止していると議事録は永久に届かないのに、画面は待機中に見える。
停止中はその旨を出すようにした。

画面共有向けには、開発中の表記(Sprint番号)と「チャンク」という語を画面から外し、
ドキュメント本文の文字を大きくした。

## 実装メモ(通信不安定時の継続、2026-08-02)

WebSocketを40秒おきに叩き切り、6分で**8回の切断**を起こして通した
(Chromium の `setOffline` は確立済みWebSocketを切らないため、
Playwright の `routeWebSocket` で仲介して切る)。

- 8回とも約1秒で再接続。画面の行が巻き戻ることも重複することもない
- 切断中の音声はバッファされ、復帰後に送られる。破棄の警告は出ていない
- **サーバー側 `transcript.md` に欠けが無い。** 確定86発言に対し画面は87行
  (末尾は未確定分)で、切断の前後で発言が飛んでいない
- JSエラーゼロ

残る未チェックは実API検証(STT精度・課題抽出の品質・コスト)で、VPS + キー投入後。

## 実装メモ(生成物の作り分け、2026-08-02)

雛形が1種類しかないと、**どんな商談でも同じ画面が出てくる。** 2回目の商談で
「さっきと同じものが出た」と気づかれた時点で、体験の核が崩れる。
要件から形を選び分けるようにした。

| 形 | 出るもの | 拾う語(例) |
| --- | --- | --- |
| 一覧・管理(既定) | 一覧 + 絞り込み + 追加・編集 | (決め手が無ければここ) |
| 申請・承認 | 申請フォーム + 承認待ち/承認済み/却下 + 承認・却下 | 申請、承認、稟議、決裁 |
| 点検・チェック | 進捗バー + チェック項目 + 気づきの記録 | 点検、確認漏れ、巡回 |
| 集計・可視化 | 件数/合計/平均 + 分類ごとの内訳(棒) | 集計、可視化、推移、把握 |

判定は**キーワードで行い、LLMには聞かない**(商談中に1往復増える割に得るものが小さく、
外したときに追えなくなる)。**目的に出た語は機能要件の2倍に数え、2点未満なら一覧へ落とす。**
語がひとつ紛れただけで形が変わると、要件を読み違えた画面が出てしまう
— 「話を聞いていない」という印象は、同じ画面が出るより悪い。

4形すべてを Chromium で実際に操作して確認した(絞り込み・追加・承認・
チェック・集計の加算)。JSエラーゼロ、外部通信ゼロ。
