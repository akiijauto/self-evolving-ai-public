# プロジェクト方針整理

当初は

Circlebackから議事録取得

↓

MVP生成

を考えていた。

しかし営業デモとしてはインパクトが弱い。

---

## 方針変更

リアルタイム音声ストリーミングを最優先する。

商談中から

議事録

課題抽出

要件定義

MVP生成

まで並列実行する。

---

## Circlebackの役割

Circlebackは

長期コンテキスト管理

議事録蓄積

ナレッジ化

として利用する。

リアルタイム処理とは分離する。

---

## Markdown思想

入力は自由

出力はMarkdown

AI同士はMarkdownだけを見る。

これにより

入力元を変更しても
システム全体は変更不要となる。

---

## 今後の優先順位

① 音声ストリーミング

② リアルタイム文字起こし

③ Markdown生成

④ オーケストレーター

⑤ MVP生成

⑥ Circleback連携

⑦ Notion連携

---

## 最重要価値

作るものはアプリではない。

営業中に

「話しているだけで試作品が完成する」

という体験そのものがプロダクトである。

# 決定記録

以降、方針を変更した際はここに追記する。
「いつ・何を・なぜ」を1エントリ3行以内で残すこと。

## 2026-08-01 リアルタイム優先へ方針転換

- **何を**: Circleback起点のバッチ処理から、リアルタイム音声ストリーミング起点へ変更した。
- **なぜ**: 商談後に成果物が届くのでは、体験としてのインパクトが出ないため。
- **影響**: Circleback連携はPhase6へ後退。WebSocket基盤がPhase1の最優先項目になった。

## 2026-08-01 Markdownを唯一の共通形式に決定

- **何を**: エージェント間のデータ受け渡しをすべてMarkdownファイルに統一した。
- **なぜ**: 入力元(音声 / Circleback / Notion / 手入力)が増えても後段を変更せずに済むため。
- **影響**: 入力アダプタとエージェントが完全に分離された。JSON等の構造化形式は採用しない。

## 2026-08-01 ドキュメント一式を先に整備

- **何を**: 実装より先に8ファイルの設計ドキュメントを整備した。
- **なぜ**: 実装をAIエージェントに委譲する前提のため、仕様の正本が必要だったため。
- **影響**: ARCHITECTURE.md が実装時の参照起点となる。

## 2026-08-01 生成MVPを外部公開せず、Gateway自前配信にする

- **何を**: 外部ホスティングへのデプロイをやめ、Gateway Serverがセッショントークン付きで静的配信する方式に変更した。
- **なぜ**: 見せる相手は営業担当自身のタブレットであり、顧客端末へ配布する必要がないため。商談内容から作られたアプリをネット上に置くリスクが消える。
- **影響**: 外部ホスティングAPI依存・デプロイ待ち時間・失効期間管理がすべて不要になった。生成アプリは静的ビルド可能なSPAに限定する(SSR不可)。`DeployProvider` インターフェースは維持し、将来必要になれば実装差し替えで対応する。

## 2026-08-01 MVP生成はトリガー承認時に開始する(A案)

- **何を**: 商談終了を待たず、トリガー発話の承認時点で生成を開始し、商談中に並行実行する方式を採用した。
- **なぜ**: 「商談終了時点でURLまで生成済み」という PROJECT.md のゴールは、終了後に生成を始めては物理的に達成できないため。
- **影響**: 承認から10分以内にデプロイ完了を目標値とした。「商談終了後URL生成30秒以内」は、生成済み成果物の提示までの時間を指す。

## 2026-08-01 誤トリガーは明示承認で防ぐ

- **何を**: トリガー検出時の5秒自動承認をやめ、営業担当が明示的に承認するまで生成を開始しない方式に変更した。
- **なぜ**: 雑談で「アプリ作って」と言われただけで商談中のPWA画面が生成モードに切り替わるリスクを、原理的に排除するため。
- **影響**: 営業担当にタップ操作が1つ増える。`trigger.detected` から `autoApproveInSec` を削除した。

## 2026-08-01 minutes.md を廃止し summary.md へ統合

- **何を**: 議事録専用ファイル `minutes.md` を作らず、議事録相当の内容を `summary.md` の「会話の要点」セクションに統合した。あわせて `todo.md` の所有者を Transcript Agent に確定した。
- **なぜ**: 「小さく作る」原則に従いファイル数を増やさないため。また REQUIREMENTS.md のMarkdownフォーマット一覧と一致させるため。
- **影響**: Requirement Agent の入力が `issues.md` / `ideas.md` / `transcript.md` / `context.md` になった。`todo.md` は商談終了時にまとめて生成する(未確定の約束を商談中に顧客へ見せないため)。

## 2026-08-01 追記専用ファイルへの手入力は `POST /inputs` へ分ける

- **何を**: `PUT /documents/transcript.md` を `409` で拒み、会話への補足は `POST /inputs` から1発話として追記する経路に分けた。
- **なぜ**: DATAFLOW.md は `transcript.md` を「追記専用。既存行を書き換えてはならない」と定める一方、入力アダプタ表では手入力の経路を `PUT` と書いていて矛盾していた。既存行を書き換えられると差分処理のカーソル(処理済みバイト位置)が指す内容が変わり、二重処理か取りこぼしが起きる。
- **影響**: DATAFLOW.md の入力アダプタ表を、追記専用と全文置換で経路が違う形に書き直した。全文置換ファイル(`requirements.md` 等)の `PUT` はそのまま使える。

## 2026-08-01 入力アダプタをAgentの所有者表の外に置く

- **何を**: 書き込み主体に `input_adapter` を追加し、所有者以外のファイルへも書けることにした。ただし追記専用/全文置換の区別は他と同じく守らせる。
- **なぜ**: AGENTS.md の所有者表は「どのAgentが書くか」の取り決めであり、外部入力の正規化はその手前の層にある。アダプタを無理にどれかのAgentに見立てると、所有者表の意味が薄れる。
- **影響**: 新しい入力元(Circleback / Notion)を足すときに触るのは `sessionDocuments.ts` の入力アダプタだけで済む。Agent側の取り決めは変わらない。

## 2026-08-01 セッション記録とMarkdownの寿命を揃える

- **何を**: メモリ上のセッション記録の保持期間を、Markdownの保持期間(30日)と同じにした。掃除も同時に行う。
- **なぜ**: 認証に使うトークンはセッション記録側にあり、先に消えるとMarkdownが残っていても読めない。逆にMarkdownだけ先に消えると、トークンはあるのに中身が無い状態になる。
- **影響**: 商談1件あたり数百バイトが30日間メモリに残る。**サーバーを再起動すると失われるため、再起動後はMarkdownを読み出せない。** セッションのメタ情報の永続化は積み残しとした。

## 2026-08-01 `LLMProvider` に使用量(トークン数)を返させる

- **何を**: `complete()` の戻り値を文字列から `{ text, model, usage }` に変えた。取得できないプロバイダは `usage: null` を返す。
- **なぜ**: 未解決の論点「商談終了時の差分再生成」は**コストを実測してから決める**と置いている。測る手段を後付けにすると、判断のたびに計装からやり直すことになる。プロンプトキャッシュが効いているかも、キャッシュ読み出しのトークン数を見ないと分からない。
- **影響**: ARCHITECTURE.md の `LLMProvider` の定義を更新した。Agent側は変わらない(プロンプトとモデル名しか指定しない)。

## 2026-08-01 課題の突き合わせは見出しで行い、IDはこちらで採番する

- **何を**: LLMには課題の見出しと内容だけを返させ、`ISS-001` のような番号はOrchestratorが振る。既存項目かどうかは見出しの一致で判定する。
- **なぜ**: IDで突き合わせると、LLMが別の課題に既存のIDを付け直したときに中身が混ざる。番号をLLMに任せると、実行のたびに同じ課題の番号が入れ替わり、商談中に画面共有している一覧の並びが動く。
- **影響**: プロンプトに「既出の課題は見出しをそのまま使う」を明記した。表記ゆれは記号と空白を無視して吸収するが、**大きく言い換えられた場合は別の課題として登録される。** 実APIでの精度は未検証。

## 2026-08-01 `document.updated` は通知だけにし、本文を載せない

- **何を**: Markdownの更新をWebSocketで知らせるとき、ファイル名と更新時刻だけを送る。本文はクライアントが `GET /documents/{name}` で取り直す。
- **なぜ**: 本文を流すと、切断中の更新を取りこぼしたときに追いつく手段が無くなる。通知と取得を分ければ、再接続後に取り直すだけで最新に追いつける。
- **影響**: 更新のたびにHTTPが1往復増える。商談中の更新頻度(60秒ごと)では問題にならない。

## 2026-08-01 `POST /generate` を Sprint 5 で先に作る

- **何を**: Sprint 6 の予定だった生成ジョブの入口を Sprint 5 で作った。ただし段階は要件定義と画面設計まで。
- **なぜ**: Requirement Agent と UI Agent は Sprint 5 の成果物だが、動かす手段が無いと完了条件を確かめられない。トリガー検出を待つと、検証できないコードを1スプリント抱えることになる。
- **影響**: `confirm: true` を必須にしてあるため、承認なしで生成が始まる口にはなっていない。Sprint 6 でトリガー検出・確認UI・コード生成の段階を後ろに繋ぐ。

## 2026-08-02 生成物にビルド工程を持たせない

- **何を**: 生成するアプリを、素の HTML / CSS / JavaScript(ビルド工程なし)に限定した。`ai_instruction.md` の既定と ARCHITECTURE.md の技術選定を書き換えた。
- **なぜ**: 元の指定は「React + Vite + TypeScript(静的ビルド必須)」だったが、商談中に `npm install` と `vite build` を走らせることになる。回線とサーバー(メモリ2GB)次第で「承認から10分以内にURL」の予算を使い切り、しかも失敗の仕方が読めない。**顧客の目の前で止まる可能性が一番高い工程を、まるごと無くす。**
- **影響**: 生成物の見た目は素朴になる。凝った画面が要るとわかった時点で、ビルド工程を持つ `CodeProvider` を追加すればよい(検証層とデプロイ層は変えずに済む)。

## 2026-08-02 事故を止めるのは規則で、LLMのレビューではない

- **何を**: 生成物の検証(`validate.ts`)を必ず走らせ、外部参照・サーバーサイド実行・シークレットの混入を規則で弾くことにした。Review Agent(LLM)の指摘はその上に積む。
- **なぜ**: 「生成コードにシークレットが含まれていない」「SSRを使っていない」は**品質ではなく事故**の問題で、確率的な判断に委ねられない。LLMが落ちていても効いている必要がある。
- **影響**: Review Agent が失敗しても配信まで進める(AGENTS.md の「レビュー失敗でデモを止めない」)。規則の指摘だけで判定できるため。

## 2026-08-02 QRコードを自前で作る

- **何を**: 外部のQR生成サービスやライブラリを使わず、QRの符号化(バイトモード / レベルL / 型番1〜10)を自前で持った。
- **なぜ**: 外部サービスへ渡せば、**商談内容から作られたURLを外へ出す**ことになる。「生成MVPを外部公開しない」という決定と矛盾する。
- **影響**: 生成したモジュールを読み返す試験で符号化の正しさを確かめている。**実機のカメラで読めるかは未確認。**

## 2026-08-02 既定のコード生成は雛形にする

- **何を**: `CodeProvider` の既定を、要件定義から雛形へ流し込む実装(推論なし)にした。LLMによる生成は `CODE_PROVIDER=llm` で選ぶ。
- **なぜ**: 商談中に一度も失敗できない工程で、まず**必ず動くもの**を出せる経路を持っておきたかった。実APIが落ちていても成果物が出る。
- **影響**: 生成物の形は雛形が持つものに限られる。当初は1種類だったが、同じ画面ばかり出るのを避けるため4種類へ増やした(下の「雛形を4種類にし、形はキーワードで選ぶ」)。

## 2026-08-02 トリガー検出時に議事録を提示する

- **何を**: トリガーを検出した時点で `summary.md` をその時点までの内容で作り直し、確認UIに「ここまでの議事録」として表示するようにした。
- **なぜ**: 検出フレーズだけでは、営業担当が「何が作られるのか」を判断できない。承認は内容を見てするべきで、見えないものへの承認は明示承認の意味を薄める。
- **影響**: トリガー検出のたびにLLM呼び出しが1回増える(Transcript Agent の summary のみ。`todo.md` は作らない — 未確定の約束を商談中に顧客へ見せないため)。**生成ジョブ本体は引き続き承認まで動かない。** 議事録の生成が失敗しても確認UIは出たままで、承認・キャンセルはできる。

## 2026-08-02 全イベントをファイルへ時系列保存する

- **何を**: 構造化ログを標準出力に加えて `{LOG_DIR}/events-YYYY-MM-DD.jsonl` へ追記するようにした(REQUIREMENTS.md のログ要件)。
- **なぜ**: 商談後に「あの時なにが起きたか」を追える必要がある。標準出力はプロセスと一緒に消える。
- **影響**: `sessionId` で1商談ぶんのイベントを抜き出せる。音声データは引き続きログに含まれない。保存失敗で商談は止めない。

## 2026-08-02 セッションのメタ情報を永続化し、再起動は「終了」として扱う

- **何を**: トークンを含むセッションのメタ情報を `{DATA_DIR}/session-meta/{sessionId}.json` へ保存し、起動時に読み戻すようにした。実行中に落ちたセッションは `endReason: "server_restart"` で終了扱いにする。
- **なぜ**: Markdownはファイルに残るのに、それを読むためのトークンがメモリにしか無いと、再起動のたびに記録への到達手段ごと失われる。一方、録音の継続まで再起動をまたいで保証しようとすると、STT接続・カーソル・seq の復元が要り、複雑さが商談中の安定性を脅かす。
- **影響**: 守るのは**記録への到達性だけ**。再起動後も閲覧・ZIP持ち帰りはできるが、録音は再開しない(営業担当は新しいセッションを作る)。書くのは作成時と終了時の2回で、同期I/Oで足りる。

## 2026-08-02 レート制限はIPで分けず、サーバー全体でひとつの窓にする

- **何を**: `POST /sessions`(唯一トークン無しで叩ける入口)に 30回/時間 の回数制限を掛けた。IPごとには分けない。
- **なぜ**: リバースプロキシ配下でのIPの取り出しは、設定を誤ると全員が同一IPになり制限の意味が変わる。営業1〜2名の運用で作成は1日数回のはずで、全体でひとつの窓を超えるのは事故か攻撃だけ。
- **影響**: 攻撃を受けている最中は正規の作成も塞がる。それでも既存セッションのトークンは生きているため、進行中の商談は影響を受けない。展示会などでは `SESSION_CREATE_LIMIT` を引き上げる。

## 2026-08-02 本番は1サブドメインの同一オリジンに載せる(Xserver VPS)

- **何を**: PWA・API・WebSocket・生成MVP配信を、既存ドメイン配下のサブドメイン1つ(推奨ラベル `mvp.`)へ nginx 経由で同一オリジン配信する構成にした(DEPLOY.md)。
- **なぜ**: 証明書1枚・CORS不要・`wsUrl` の自動組み立て・QRのURLも同一ホストで、構成の失敗点が最少になる。マイクとPWAはHTTPS必須なので、TLS終端は避けられない。
- **影響**: Gateway は 127.0.0.1 にのみバインドし、外へは nginx しか出さない。`VITE_API_BASE_URL` は未設定のままでよい。

## 2026-08-02 課題の根拠は3件で打ち止めにする

- **何を**: `issues.md` の「根拠」は同じ課題につき3件までとし、時刻を外して比較して重複を弾く。
- **なぜ**: 30分の通しリハーサルで、会話が同じ話題へ戻るたびに根拠が積み上がり、1課題あたり33件になった。重複判定は元からあったが、根拠の値に発言時刻が入るため、**まったく同じ発言でも時刻が違えば別物**と判定されていた。課題タブは商談中に顧客へ画面共有する場所で、根拠の羅列で埋まると課題そのものが読めない。
- **影響**: その課題がどう立ち上がったかは先頭3件で分かる。何度言及されたかを数える用途には使えないが、それは `transcript.md` の仕事。

## 2026-08-02 確認を出した直後はトリガーを無視する

- **何を**: トリガー検出で確認UIを出したあと、既定3分間は次の検出を捨てる(`TRIGGER_COOLDOWN_MS`)。
- **なぜ**: 30分の通しリハーサルで59回の再検出が起き、そのたびに議事録の作り直し(LLM呼び出し)まで走った。trigger.ts の「拾いすぎるくらいで構わない」は**最初の1回を取りこぼさない**ための割り切りであって、同じ商談で確認UIを数十秒おきに出し続ける口実ではない。
- **影響**: 言い直して作り直したい場合は3分あける必要がある。生成に3分以上かかればクールダウンは切れているため、失敗直後の言い直しは妨げない。

## 2026-08-02 縮退中は「準備しています」を出さない

- **何を**: AIが停止している間、トリガー確認ダイアログの議事録欄に「用意できませんでした」と出す。
- **なぜ**: 「準備しています…」は一時的な状態を表す文言で、恒久的な失敗を表さない。LLMが落ちていると議事録は永久に届かないのに、営業担当は届くものとして待ってしまう。画面の別の場所には「AIが停止しています」と出ており、同じ画面で矛盾していた。
- **影響**: 承認・キャンセルは引き続きできる。議事録なしで判断することになるが、**判断できない状態を隠さない**ほうが商談中の意思決定を助ける。

## 2026-08-02 雛形を4種類にし、形はキーワードで選ぶ

- **何を**: 生成物の形を「一覧・管理」「申請・承認」「点検・チェック」「集計・可視化」の4種類にし、要件の語彙から選ぶ。判定は**キーワードで行い、LLMには聞かない**。
- **なぜ**: 1種類しかないと、**どんな商談でも同じ画面が出てくる。** 2回目の商談で見せたときに「さっきと同じものが出た」と気づかれ、「話した内容から作られた」という核の説得力が消える。判定をLLMに任せなかったのは、商談中に1往復増える割に得るものが小さく、外したときに何が起きたか追えなくなるため。キーワードなら `codegen.shape` のログで後から確認できる。
- **影響**: 外しても「一覧」に落ちるだけで、生成そのものは必ず成功する。同じ要件からは必ず同じ形が出る(実行のたびに変わらない)。4形すべてで validate.ts を通り、ブラウザで操作して動作を確認済み。

## 2026-08-02 形は語ひとつでは変えない(目的を重く見る)

- **何を**: 形の判定で、目的に出た語は機能要件の2倍に数え、2点に届かなければ一覧へ落とす。
- **なぜ**: 素朴に語の数だけで決めると、**手段の側に紛れた1語で形が引っくり返る。** 在庫台帳の要件に「共有ダッシュボードを用意する」というアイデアが混ざっただけで集計画面が出た(モックの要件で実際に起きた)。要件を読み違えた画面は、同じ画面が出るより悪い印象を与える — 「話を聞いていない」ように見えるため。
- **影響**: 目的にはっきり出ていれば1語でも倒れる。手段の側だけなら2語必要。判断に迷う要件は一覧へ落ちるが、一覧は「見たい・管理したい」という大半の商談で成立する。

## 2026-08-02 集計の軸に「名称」を選ばない

- **何を**: 集計・可視化型の内訳の軸は、分類・部門・状態のような**まとまる項目**を先に探し、名称は最後の手段にする。
- **なぜ**: 品名や氏名はほぼ一意なので、軸にすると1件ずつの棒が並ぶだけで「どこが多いのか」が見えない。「部門ごとの件数を見たい」という会話から作ったのに、名称ごとの棒が出てくると要件を読み違えたように見える。
- **影響**: データモデルに分類系の項目が無ければ、先頭以外の文字項目へ落ちる。

## 2026-08-02 実APIの応答は `stop_reason` を見てから読む

- **何を**: `AnthropicLLMProvider` で、`content` を読む前に `stop_reason` を判定するようにした。拒否(`refusal`)は再試行しない失敗、上限切れ(`max_tokens`)は途中出力を捨てて再試行、と扱いを分ける。あわせて `max_tokens` の既定を 4096 → 16000 に上げた。
- **なぜ**: 一度も実接続していないコードを公式仕様と突き合わせて分かった。**拒否された応答は HTTP 200 で `content` が空で返る** — 素直に読むと「空の応答」に見え、再試行可能として3回粘ることになる(原因も対処も違う)。**上限で切れた応答は書きかけのまま返る** — 閉じていないMarkdownや途中までのコードが検証・配信へ流れる。さらに Claude Opus 5 は指定しなければ思考が働き、`max_tokens` は**思考と本文の合計**にかかるため、4096では要件定義やコード生成が途中で切れる。
- **影響**: 実キー無しでも `fetch` を差し替えて検証できるようにした(8件のテスト)。商談中に一度も失敗できない工程なので、途中までの出力は黙って受け取らない。

## 2026-08-03 nginx の追加をスクリプトにし、危なければ止める

- **何を**: 手順5(vhost追加 + 証明書)を `scripts/setup-nginx.sh` にした。既存設定は読むだけ、`/etc/nginx` を控えてから新しいファイルを1つ足し、`nginx -t` が通らなければ**自分で取り消してから**止まる。同じドメインを既に名乗る server があれば、そのファイル名を出して何もせず終わる。
- **なぜ**: 配置先には既に別のサイトが動いている。手順書に「確認すること」を書いても、確認するのは人で、商談前の慌ただしい時間に読み飛ばされる。**落とし方が「既存サイトが止まる」なので、人の注意力に預けてよい種類の作業ではない。**
- **影響**: 実サーバーと同じ nginx 1.24.0 (Ubuntu) を立て、default_server 付きの既存サイトと同居させて通した。**`listen [::]:80` を無条件に書くと、IPv6を持たないホストで `nginx -t` ごと落ちることが分かった**(この状態で reload すれば既存サイトも巻き添えになる)。既存設定が `[::]:80` を張れているときだけ真似るようにした。証明書は取得済みなら取り直さず設定へ入れ直す — 手順3でファイルを作り直すため、そうしないと再実行のたびにHTTPSが消える。

## 2026-08-03 preflight は status ではなく中身を見る

- **何を**: `preflight.mjs` の Service Worker 確認を、「本文が空でない」から「HTMLが返っていない」へ変えた。
- **なぜ**: nginx の `try_files $uri /index.html` は**未知のパスをPWAへ落とす**。つまり配置し忘れたファイルも 200 で返る。`sw.js` を消して試したところ、修正前は 877バイトの index.html を受け取って **OK と判定していた。** 疎通確認が「配置漏れ」を見逃すなら、それは確認になっていない。
- **影響**: 実サーバーと同じ構成(nginx + TLS + ビルド済みPWA)に対して全項目を通し、`sw.js` を外すと NG になることも確かめた。「200が返った」を成功と読む確認は、フォールバックのある配信では常に嘘をつきうる。

## 2026-08-03 Basic認証はPWA本体とセッション作成だけにかける

- **何を**: `setup-nginx.sh` に `RTMVP_BASIC_USER` を足し、`location /` と `location = /api/v1/sessions` の2つにだけ Basic 認証をかけられるようにした。`/api/` の残り・`/preview/`・`/ws/`・`/healthz` にはかけない。
- **なぜ**: TLS証明書は Certificate Transparency ログに載るので、**サブドメインの存在は取得の数分後に公開情報になる。** 無認証だと `SESSION_CREATE_LIMIT`(30回/時間、サーバー全体でひとつの窓)を他人に使い切られ、商談の開始時に作れなくなる。無認証で触れるのは「PWA本体」と「セッション作成」の2つだけなので、そこだけ塞げば足りる。
- **影響**: 最初は `/api/` 全体にかけていた。**これはPWAを完全に壊す。** PWAはセッション操作のたびに `Authorization: Bearer <セッショントークン>` を送るが、Authorizationヘッダは1つしか無いので Basic 認証と奪い合いになり、nginx が全ての呼び出しを401で弾く — 録音は始まるのに議事録が一切読めない状態になる。実サーバーと同じ nginx を立てて `Authorization: Bearer` を投げ、401とnginxのHTMLが返ることを確認してから範囲を絞った。`/preview/` に認証がかかっていないことは、確認手順にも組み込んだ(かかっていたら顧客がQRを読んでも開けない)。

## 2026-08-03 reload の直後に確認しない

- **何を**: `setup-nginx.sh` の確認手順の前に3秒待つようにした。`getent` の失敗が `pipefail` で握り潰されて黙って終わる問題、応答が取れないのに「合格」と出る問題もあわせて直した。
- **なぜ**: nginx の reload は古いworkerを残したまま返る。待たずに確認すると**古い設定のまま応答が返り、認証がかかっているのに「かかっていない」と報告する。** 実際に一度そう出た。確認の結果が信用できないなら、確認しないのと同じである。
- **影響**: かける→外す→かける を続けて流し、毎回同じ結果になることを確かめた。「届かなかった」は合格でも不合格でもなく**確認できていない**ので、そう報告して止まるようにした。

## 2026-08-03 QRに載せるトークンを、操作用と分ける

- **何を**: `Session` に `previewToken` を足し、`/preview/` はこれだけを検証するようにした。API と WebSocket は従来の `token` のまま。QRとリンクに載るのはプレビュー用。
- **なぜ**: 独立レビューで見つかった。**プレビューURLは商談中の画面に映り、開いた端末の履歴にも残る。** それが操作用トークンと同じ値だったので、写真1枚あれば有効期間(既定4時間)内に「文字起こし全文の取得」「議事録の改ざん」「WebSocketへの接続で以降の更新を横取り」「録音の停止」まで全部できた。RETROSPECTIVE には「ZIPのトークンをURLに載せない」と書いてあったのに、プレビューURLでは同じことをしていた。
- **影響**: 分離そのものをテストで固定した(操作用でプレビューは開けない / プレビュー用でAPIもZIPも通らない)。分離前に保存されたセッションは、読み戻すときに別の値を割り当てる — 操作用で埋めると分離した意味が消えるため。Markdownの閲覧と持ち帰りはそのまま続けられる。

## 2026-08-03 Service Worker を `/preview/` に触らせない

- **何を**: `sw.js` が `/preview/` `/api/` `/ws/` を素通しするようにし、navigate の応答を `/index.html` として保存するのは PWA 本体のときだけにした。
- **なぜ**: 同一オリジンに載せた副作用。**URLを見ずに `cache.put("/index.html", ...)` していたので、顧客に見せた生成MVPがPWA本体として保存されていた。** 次にオフラインでPWAを開くと、業務ツールではなく前回商談のデモが立ち上がる。生成物のJS/CSSも cache-first で無期限に残り、**セッション失効後もトークン検証を通らずキャッシュから配信されていた。** `cache-control: no-store` は Cache API には効かない。
- **影響**: `CACHE_NAME` を上げて既存の汚染ごと捨てる。修正前のコードに対してテストを走らせると狙った4件だけが落ちることを確認済み(テストが素通りしていないことの確認)。

## 2026-08-03 停止したあとの議事録を、通知ではなく取りに行く

- **何を**: 商談終了後は `GET /documents` を3秒ごとに引くようにした(最長2分)。持ち帰りボタンは生成の有無に関わらず出す。開き直したときは `sessionStorage` からセッションへ戻る。
- **なぜ**: この3つが重なると**商談の記録を回収する手段が全部塞がる。** `endSession` は `runClosing`(LLM呼び出し)を投げた直後に WebSocket を閉じるので、`summary.md` と `todo.md` の完成通知は閉じたソケットへ送られ、PWAには永久に届かない。持ち帰りボタンは生成結果の中にあったので、トリガーが出なかった商談では画面に現れない。トークンはReactの状態にしかないので、開き直せば消える。**手順書には「少し待つと議事録が仕上がる」「記録は消えない」と書いてあった。**
- **影響**: 通知が来ないものは取りに行くしかない。終了済みセッションでもMarkdownを読めるようにしてあった(Sprint 4)ので、その方針がそのまま逃げ道になった。

## 2026-08-03 書いたファイルを他ユーザーに読ませない

- **何を**: セッションメタ(トークン平文)・Markdown・Agent実行履歴・ログ・生成物を 0600 / 0700 で書くようにし、systemd に `UMask=0077` を足した。
- **なぜ**: 既定の umask 022 では 0644 になる。**この構成は「既に別のサイトが動いているサーバー」へ入れることを前提にしている。** 同居する `www-data` などから `cat` するだけで全セッションのトークンと商談の全文が読めた。DEPLOY.md が権限に言及していたのは `/etc/rt-mvp/env` だけだった。
- **影響**: 実際に書かれたファイルの権限をテストで確認する。守るものを決めたら、置き場所の権限まで含めて決めきらないと意味がない。

## 2026-08-03 「宣言してあること」と「実装されていること」を突き合わせる

- **何を**: 独立した2つのレビュー(セキュリティ / ドキュメント整合)を回し、出てきた指摘を自分でコードに当たって確認してから直した。
- **なぜ**: どちらも**書いた本人には見えない類の欠陥**を出した。「同時接続は後勝ちで前を切る」はコメントにあるだけで `close()` を呼んでいなかった(前の画面は「接続中」のまま更新だけ止まる)。手順書の「持ち帰り(ZIP)」というボタンはリポジトリ全体に存在しなかった。DEPLOY.md の受け入れテストに書いた「試しに作ってみましょう」はトリガー語に一致せず、**構築直後の確認が必ず失敗する**状態だった。
- **影響**: 指摘は鵜呑みにせず全件コードで裏を取った(結果は全件正しかった)。宣言だけして実装していない箇所は、テストが無ければ永遠に気づけない。直した項目にはすべてテストを付けた。

## 2026-08-07 音声で通らないときの道を、音声の外に用意する

- **何を**: 実機確認で「アプリ作って」と言っても生成へ進まない事象が出た。(1) 承認待ちのまま確認UIが消えたジョブが以後のトリガーを全て握り潰す点を、同じジョブの `trigger.detected` 再送で直した。(2) PWAに手動の「ここまでの内容で試作品を作る」ボタン(既存の `POST /generate`)を付けた。承認待ちの残骸ジョブは手動開始で置き換える。(3) トリガー語へ「アプリ作成」を追加し、カタカナ/ひらがなの表記ゆれを吸収した。
- **なぜ**: 音声トリガーは誤認識・クールダウン・検出漏れ・UI消失と**不発の理由が多層にある**。どの層で落ちても営業担当が先へ進める道は、音声の外(ボタン)にしか置けない。不発の各層を個別に塞ぐだけでは、次の未知の層でまた同じ「何も起きない」が起こる。
- **影響**: キャンセル後のクールダウン(2026-08-02「確認を出した直後はトリガーを無視する」)は変えていない。すぐ作り直したい場合の正規の道はボタンとする。

## 2026-08-07 文字起こしの誤認識は、人がその場で直せるようにする

- **何を**: 実機確認で「あいこ→アイコン」のような誤認識が要件定義に残り、直す手段がなかった。ドキュメント表示に「修正する」ボタン(既存の `PUT /documents/{name}`、`transcript.md` を除く)を付けた。加えて、生成ジョブが要件定義を作り直すとき現在の `requirements.md` を渡し、「手動修正された用語を正とする」と指示した。
- **なぜ**: 修正UIだけ付けても、次の生成で Agent が会話ログから作り直して**手動修正を上書きしてしまう**。直せることと、直したものが残ることは別の問題で、両方を塞がないと「訂正できない」は解決しない。
- **影響**: 手動PUTは `document.updated` を発しないため、保存した本人の画面へは PWA 側で即時反映する(`applyLocal`)。固有名詞の誤認識が多い場合は、次の商談前に `context.md` へ正しい用語を書いておく運用も効く。

# 検討したが採用しなかった案

| 案 | 不採用の理由 |
| --- | --- |
| 音声認識を自前でホストする | 初期のサーバー要件(メモリ2GB)を満たせない。重い処理は外部APIへ委譲する方針と矛盾する |
| エージェント間をJSONで受け渡す | 人間が商談中に読めない。Markdownならそのまま画面共有できる |
| 商談終了後にまとめて生成する | 「その場で完成する」という最重要価値が失われる |
| 生成MVPを本番運用可能な品質にする | スコープが無限に膨らむ。試作品の提示までに限定する |
| 生成MVPを外部ホスティングへ公開する | 見せる相手は自分のタブレット。商談内容から作られたアプリをネット上に置く理由がない |
| トリガー検出をやめて手動ボタンのみにする | 「話すだけで動く」というデモの驚きが失われる。検出は残し、承認を必須にすることで両立させた |
| 会話の全文をLLMに毎回投入する | コストと遅延が線形に増える。差分投入+プロンプトキャッシュを前提とする |
| Markdownをデータベースに入れる | 「唯一の正本はMarkdown」という原則が崩れる。人がそのまま読めることと、後から手で直せることを優先した |
| 差分カーソルを行番号で持つ | 追記のたびに行を数え直すことになる。バイト位置なら追記のバイト長を足すだけで進む |
| Agent間のやり取りをJSONにする | 「AI同士はMarkdownだけを見る」に反する。新規追加と既存への追記の区別は、見出しの一致で表現できる |
| Issue Agent に全文を毎回渡す | コストと遅延が会話の長さに比例して増える。差分 + 既存の課題一覧で足りる |
| `document.updated` に本文を載せる | 切断中の更新を取りこぼすと追いつけない。通知と取得を分ける |
| トリガー検出だけで生成を始める | 雑談で「アプリ作って」と言われただけで商談中の画面が切り替わる。検出と承認を分ける |
| 生成物のビルドをサーバーで走らせる | 顧客の目の前で止まる可能性が一番高い工程になる。ビルドの要らない形に限定した |
| QRコードを外部サービスで作る | 商談内容から作られたURLを外へ出すことになる |
| ZIPのダウンロードをトークン付きURLにする | トークンがコピーやログに残る。取得してから保存させれば載せずに済む |

# 未解決の論点

実装を進める中で判断が必要になる項目。決まり次第、上の決定記録へ移す。

- **商談終了時の差分再生成**: トリガー後の会話を反映してMVPを再生成するか。**LLM呼び出しコストを実測してから判断する**(Sprint6完了後)。現状はトリガー承認時の1回のみ生成する。
- **話者分離の必要度**: 自社側と顧客側の発話を区別できないと、課題抽出の精度がどれだけ落ちるか未検証。**Sprint3で実APIの分離精度を実測して採否を決める**。
- **課題抽出の品質**: モックでは形しか検証できない。実LLM APIで、既出の課題を言い換えずに返せるか(二重登録の起きにくさ)と、商談中に画面共有できる日本語になるかを確かめる必要がある。
- **プロンプトキャッシュの効き**: ~~未計測。~~ → **現状のプロンプト長では効かないことが分かった。** キャッシュ対象の前置きには最小サイズがあり(Claude Opus 5 は512トークン、Claude Sonnet 5 は1024トークン)、下回るとエラーも警告もなく素通りする。各Agentの指示は190〜530文字しかない。`context.md` が大きい商談でのみ効く見込みで、実APIの `cache_read_input_tokens` で最終確認する(`scripts/verify-llm.mjs`)。
- **実機でのQR読み取り**: 符号化は読み返し試験で確かめたが、カメラで読めるかは端末が要る。
- **生成物の作り分け**: 雛形を4種類にして要件から選び分けるようにしたが、そのどれにも当てはまらない商談で何が出るべきかは決めていない(現状は一覧へ落ちる)。実LLMでのコード生成を検証し、雛形とLLM生成の役割分担を決める。
- **オフライン耐性**: 60秒までのバッファで切断8回を乗り切ることは確認した(Sprint 7)。それを超える長時間の断でどこまで耐えるべきかは未決。
- **複数話者の同時発話**: 会議室での商談を想定した場合の認識精度が未検証。
- **顧客へのURL共有**: 現状は自前配信のため顧客端末から開けない。商談後に触ってもらいたい要望が出た場合、外部公開経路を追加するか判断する(`DeployProvider` の実装追加で対応可能)。
